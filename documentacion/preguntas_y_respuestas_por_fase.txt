RECORRIDO VIRTUAL 360° DE UNA VIVIENDA

Este archivo se ampliará al terminar cada fase. Las respuestas describen únicamente
funciones que ya fueron analizadas o implementadas; no atribuyen capacidades futuras
a la versión actual.

===============================================================================
FASE 0 — ANÁLISIS Y DISEÑO
===============================================================================

1. ¿Por qué se eligió TypeScript?

Respuesta breve:
Porque permite detectar errores de estructura antes de ejecutar la aplicación.

Respuesta técnica:
TypeScript describirá la forma de pisos, habitaciones, panoramas y conexiones.
El compilador señalará propiedades ausentes o valores de tipo incorrecto, mientras
un validador comprobará posteriormente las relaciones entre identificadores.

Componente relacionado:
Modelo de datos y futuro validador del recorrido.

2. ¿Por qué no se eligió React?

Respuesta breve:
Porque la interfaz inicial es pequeña y no necesita un framework completo.

Respuesta técnica:
La biblioteca panorámica resolverá el renderizado complejo. La aplicación solo
necesita coordinar un menú, la ubicación actual y mensajes. TypeScript y módulos
DOM reducen dependencias y conceptos sin impedir una migración futura.

Componente relacionado:
Arquitectura de interfaz.

3. ¿Por qué se propuso Photo Sphere Viewer?

Respuesta breve:
Porque es gratuito, de código abierto y tiene soporte específico para recorridos.

Respuesta técnica:
Su núcleo muestra panoramas equirectangulares y su Virtual Tour Plugin representa
nodos, enlaces y posiciones manuales. También expone eventos de carga y error.

Componente relacionado:
Futuro adaptador del visor.

4. ¿Cómo se representarán las habitaciones grandes?

Respuesta breve:
Cada habitación podrá contener varios panoramas y uno será su punto de entrada.

Respuesta técnica:
La habitación tendrá un panorama representativo para navegación directa y una
colección de panoramas conectados para el recorrido espacial interno.

Componente relacionado:
Modelo de datos propuesto.

5. ¿Cómo se protegerán las fotografías?

Respuesta breve:
Se mantendrán localmente y se excluirán del historial Git.

Respuesta técnica:
No habrá nube, analítica ni CDN de imágenes. Las fotografías privadas y las
construcciones que puedan contenerlas estarán ignoradas por Git y deberán revisarse
antes de compartir cualquier copia.

Componente relacionado:
.gitignore y estrategia de privacidad.

FASE 1 — PROYECTO MÍNIMO
===============================================================================

1. ¿Qué se construyó en la Fase 1?

Respuesta breve:
La base ejecutable del proyecto y una primera interfaz adaptable.

Respuesta técnica:
Se creó una aplicación Vite + TypeScript sin framework, con HTML semántico, estilos
adaptables, un punto de entrada TypeScript y comandos para desarrollo, tipos, lint
y construcción.

Archivo o componente relacionado:
index.html, src/main.ts, src/styles/main.css y package.json.

2. ¿Dónde comienza la ejecución?

Respuesta breve:
El navegador abre index.html y este carga src/main.ts.

Respuesta técnica:
La etiqueta script de tipo module solicita el módulo principal. Vite resuelve la
importación de CSS, transforma TypeScript para el navegador y actualiza la página.

Archivo o componente relacionado:
index.html y src/main.ts.

3. ¿Cómo sabemos que TypeScript sí se ejecutó?

Respuesta breve:
El mensaje de estado cambia a “Fase 1 completada”.

Respuesta técnica:
El HTML contiene inicialmente “Comprobando la aplicación…”. main.ts busca el
elemento, valida su existencia y reemplaza el texto. Si el módulo no se ejecutara,
el mensaje inicial permanecería visible.

Archivo o componente relacionado:
src/main.ts.

4. ¿Por qué se usa Vite?

Respuesta breve:
Porque ofrece servidor local y construcción sin configurar un backend.

Respuesta técnica:
Vite sirve módulos durante el desarrollo, procesa TypeScript y CSS y genera una
versión estática optimizada en dist. El proyecto sigue siendo completamente local.

Archivo o componente relacionado:
package.json.

5. ¿Qué comprueba el comando npm run check?

Respuesta breve:
Comprueba estilo, tipos y que la aplicación pueda construirse.

Respuesta técnica:
Primero ejecuta ESLint. Después build ejecuta TypeScript con noEmit y, si no hay
errores, Vite crea la versión de demostración. Un fallo detiene la secuencia.

Archivo o componente relacionado:
package.json, eslint.config.js y tsconfig.json.

6. ¿Cómo se adapta la interfaz al teléfono?

Respuesta breve:
El diseño cambia de dos columnas a una columna.

Respuesta técnica:
Una media query se activa por debajo de 700 píxeles. La barra superior se apila,
el panel de ubicaciones pasa encima del visor y el contenido conserva un ancho
mínimo utilizable.

Archivo o componente relacionado:
src/styles/main.css.

7. ¿Por qué el visor todavía no funciona?

Respuesta breve:
Porque esta fase solo valida la base del proyecto.

Respuesta técnica:
La integración del visor es una responsabilidad separada de la Fase 2. Dividir el
trabajo permite comprobar primero herramientas, estructura, diseño adaptable y
construcción sin mezclar errores de WebGL o imágenes.

Archivo o componente relacionado:
Plan de desarrollo y área provisional de index.html.

8. ¿Qué protege actualmente la privacidad?

Respuesta breve:
Las fotos privadas tienen una carpeta local excluida de Git.

Respuesta técnica:
.gitignore excluye el contenido de public/panoramas/private y también dist. El
README de la carpeta advierte que una construcción puede contener copias privadas,
por lo que debe revisarse antes de compartirla.

Archivo o componente relacionado:
.gitignore y public/panoramas/private/README.md.

FASE 2 — PANORAMA INDIVIDUAL
===============================================================================

1. ¿Qué aporta Photo Sphere Viewer?

Respuesta breve:
Convierte la imagen equirectangular en una vista 360° interactiva.

Respuesta técnica:
Usa Three.js y WebGL para aplicar la fotografía como textura de una esfera. También
aporta arrastre, zoom, pantalla completa, controles y eventos de carga.

Archivo relacionado:
src/viewer/panorama-viewer.ts.

2. ¿Qué parte desarrollamos nosotros?

Respuesta breve:
La integración, la interfaz, los mensajes y el manejo de errores.

Respuesta técnica:
Nuestro adaptador configura el visor y traduce sus eventos. main.ts actualiza la
interfaz; index.html y main.css definen contenedor, estados y adaptación móvil.

Archivos relacionados:
panorama-viewer.ts, main.ts, index.html y main.css.

3. ¿Por qué la imagen debe tener proporción 2:1?

Respuesta breve:
Porque representa 360° horizontales y 180° verticales.

Respuesta técnica:
La proyección equirectangular asigna longitud a la coordenada horizontal y latitud a
la vertical. La esfera completa tiene el doble de extensión horizontal que vertical.

Archivo relacionado:
public/panoramas/demo/parqueadero-demo-01.png.

4. ¿Cómo se informa el progreso?

Respuesta breve:
El visor emite un evento y la aplicación actualiza el mensaje.

Respuesta técnica:
load-progress proporciona un porcentaje. El adaptador lo redondea y envía un estado
loading; main.ts lo representa mediante texto y color.

Archivos relacionados:
panorama-viewer.ts y main.ts.

5. ¿Qué ocurre si la imagen no existe?

Respuesta breve:
Aparece un mensaje comprensible y un botón para reintentar.

Respuesta técnica:
panorama-error conserva el detalle en la consola y envía el estado error. main.ts
muestra el botón, que vuelve a llamar setPanorama sin recargar la página.

Archivo relacionado:
panorama-viewer.ts.

6. ¿Cómo funciona el zoom?

Respuesta breve:
Con rueda, pellizco táctil o botones más y menos.

Respuesta técnica:
El visor modifica el campo de visión entre minFov y maxFov. Un campo de visión menor
representa mayor acercamiento.

Archivo relacionado:
Configuración del Viewer en panorama-viewer.ts.

7. ¿Por qué el visor está aislado en otro archivo?

Respuesta breve:
Para no mezclar la biblioteca con la lógica general.

Respuesta técnica:
El adaptador expone solo retry, destroy y estados simples. Cambiar de biblioteca
afectaría principalmente ese módulo, no toda la interfaz.

Archivo relacionado:
src/viewer/panorama-viewer.ts.

8. ¿Qué limitación conserva la Fase 2?

Respuesta breve:
Solo existe un panorama y no se puede avanzar a otra habitación.

Respuesta técnica:
Todavía no existe el modelo de nodos ni el Virtual Tour Plugin. La separación permite
verificar WebGL, imagen, zoom y errores antes de añadir conexiones.

Componente relacionado:
Plan de la Fase 3.


PREGUNTAS Y RESPUESTAS POSIBLES — FASE 3

¿Qué se entrega?
Un recorrido funcional Parqueadero <-> Pasillo <-> Cocina con flechas y regreso.

¿Por qué separar datos y visor?
Para cambiar fotos, nombres o conexiones sin reescribir la interfaz.

¿Las imágenes son reales?
No. Pasillo y Cocina son recursos ficticios de demostración.

¿Qué son yaw y pitch?
Yaw es el ángulo horizontal de una flecha y pitch su ángulo vertical.

¿Los ángulos son definitivos?
No. Se calibrarán visualmente al incorporar las fotografías reales.

¿Cómo se evita una ruta rota?
El validador rechaza destinos inexistentes y conexiones sin enlace de regreso.

¿Cómo se verifica la fase?
Con npm run check, que ejecuta estilo, pruebas, tipos y construcción.

¿Qué queda para la fase 4?
El menú navegable por pisos y ambientes, estado activo y adaptación móvil.

FASE 4 — PREGUNTAS Y RESPUESTAS
1. ¿Qué permite el nuevo menú?
Abrir directamente Parqueadero, Pasillo o Cocina sin recorrer puntos anteriores.
2. ¿De dónde salen sus opciones?
Del mismo TourConfig utilizado por el visor; nombres, pisos y destinos no se duplican.
3. ¿Qué es entryPanoramaId?
El panorama representativo que se abre al seleccionar un ambiente.
4. ¿Cómo se identifica la ubicación actual?
El botón activo usa estilo visual y aria-current; la cabecera se sincroniza.
5. ¿Se puede usar sin ratón?
Sí. Tab entra al menú; las flechas mueven el foco, Inicio y Fin saltan a los extremos, y Enter abre.
6. ¿Cómo se verificó?
Edge probó saltos directos, inicio, sincronización, teclado y una ventana móvil de 390 por 844 píxeles.

FASE 5 — PREGUNTAS Y RESPUESTAS
1. ¿Cuántos panoramas tiene ahora el recorrido?
Ocho: tres iniciales del primer piso, dos de escaleras y tres ambientes del segundo piso.
2. ¿Cómo se conecta el segundo piso?
Pasillo, Escalera inferior y Escalera superior forman la subida. El descanso permite elegir derecha o izquierda.
3. ¿Qué hay a la derecha?
Cuarto 1, con un enlace de regreso al descanso.
4. ¿Qué hay a la izquierda?
Cuarto 2; desde allí se continúa al Estudio y se puede regresar por la misma ruta.
5. ¿Por qué no existe otro panorama de corredor?
Porque el usuario limitó la fase a ocho panoramas. Un distribuidor adicional habría elevado el total a nueve.
6. ¿Cómo se evita dejar una zona aislada?
El validador recorre el grafo desde Parqueadero y reporta cada panorama que no pueda alcanzar.
7. ¿Las imágenes representan la vivienda real?
No. Son imágenes ficticias para validar estructura, navegación y experiencia.
8. ¿Cómo se verificó?
Seis pruebas automáticas y Edge recorrieron ambas plantas y todos los regresos sin errores.

FASE 6 — DEMO PÚBLICA CON ACCESO BÁSICO

1. ¿Se podrá abrir desde cualquier red?
Sí. Vercel proporcionará una URL HTTPS pública.

2. ¿Qué verá la persona primero?
Una pantalla de Orbinodo con campos de usuario y contraseña.

3. ¿Dónde se comprobarán las credenciales?
En el navegador mediante TypeScript y Web Crypto.

4. ¿Es una autenticación segura?
No. Es una barrera práctica para una demo; una persona técnica podría eludirla.

5. ¿Por qué es aceptable en esta etapa?
Porque las ocho panorámicas son artificiales y no contienen información sensible.

6. ¿Se guardará la contraseña en texto plano?
No. Se configurará un hash SHA-256, aunque ese hash seguirá siendo público.

7. ¿Qué se debe instalar?
Solo la CLI de Vercel como dependencia de desarrollo. No se instalará Supabase.

8. ¿Cuánto dura la sesión?
Durante la pestaña actual mediante sessionStorage.

9. ¿Se necesita comprar un dominio?
No. Puede usarse el subdominio gratuito asignado por Vercel.

10. ¿Qué debe proporcionar el propietario?
El usuario deseado, una contraseña exclusiva configurada localmente, el nombre del
sitio, una cuenta de Vercel y autorización para publicar.

11. ¿Debo enviar la contraseña por chat?
No. Se introducirá localmente al generar el hash.

12. ¿Cuándo debe cambiar esta solución?
Antes de publicar fotografías reales, datos personales o contenido que sí requiera
confidencialidad.


FASE 6 — PREGUNTAS Y RESPUESTAS AÑADIDAS

Pregunta: ¿La fase 6 ya funciona localmente?
Respuesta: Sí. El formulario, la sesión, el cierre de sesión, las pruebas y la compilación están terminados. Falta publicar la vista previa en Vercel.

Pregunta: ¿La contraseña está guardada en el código?
Respuesta: No. El código compara un hash SHA-256 leído desde una variable. .env.local está ignorado por Git. Sin embargo, al ser una aplicación estática, una persona técnica puede inspeccionar el hash o saltar la barrera.

Pregunta: ¿Por qué el visor no se crea detrás del formulario?
Respuesta: Para ahorrar memoria y para que no haya un recorrido activo antes del acceso. Se crea al autenticar y se destruye al cerrar sesión.

Pregunta: ¿Qué ocurre al recargar o cerrar la pestaña?
Respuesta: Recargar conserva el acceso en esa pestaña. Cerrar sesión o cerrar la pestaña elimina la sesión.

Pregunta: ¿Puedo usar estas credenciales para fotografías privadas reales?
Respuesta: No es recomendable. Esta solución fue elegida porque las imágenes actuales son artificiales y públicas. Material sensible necesitaría servidor, sesiones verificadas y archivos privados.

Pregunta: ¿Debo enviar mi contraseña por chat?
Respuesta: No. Se genera el hash en el computador con npm run auth:hash y solo ese hash se copia a .env.local y Vercel.

Pregunta: ¿Qué falta para verla desde otra red?
Respuesta: Iniciar sesión en Vercel, crear la vista previa, configurar las dos variables, desplegar y probar la URL desde datos móviles o una red diferente.


FASE 7 — NUEVAS PREGUNTAS Y RESPUESTAS

Pregunta: ¿Qué mejora produjo la carga diferida?
Respuesta: La pantalla de acceso ya no descarga inicialmente toda la biblioteca panorámica. El paquete principal quedó en aproximadamente 9,63 kB sin comprimir y el visor se carga después de autenticar.

Pregunta: ¿Por qué el menú móvil empieza plegado?
Respuesta: Para reservar la mayor parte de la pantalla al panorama. Sigue disponible mediante un botón accesible y se cierra después de elegir un ambiente.

Pregunta: ¿Por qué las pruebas usan credenciales aleatorias?
Respuesta: Para comprobar el acceso sin guardar en el repositorio la contraseña utilizada por la demostración real.

Pregunta: ¿La fase 7 terminó con este avance?
Respuesta: No. La experiencia principal está aprobada, pero todavía deben probarse fallos de imágenes y WebGL y hacerse la revisión manual final en dispositivos reales.


PREGUNTAS Y RESPUESTAS: ROLES PROGRAMADOR Y JEFE
=================================================

Pregunta: ¿Qué diferencia existe entre los dos usuarios?
Respuesta: Ambos recorren la misma demo. Programador ve el calibrador yaw/pitch;
Jefe no ve el botón, las coordenadas ni la mira.

Pregunta: ¿La cuenta que ya utilizaba dejó de funcionar?
Respuesta: No. La cuenta existente se considera ahora Programador y conserva su
contraseña.

Pregunta: ¿Cómo pruebo inmediatamente el usuario Jefe?
Respuesta: Mientras no se configuren variables propias, el usuario es Jefe y
utiliza temporalmente la misma contraseña de la cuenta Programador.

Pregunta: ¿Pueden tener contraseñas diferentes?
Respuesta: Sí. Se genera otro hash con npm run auth:hash eligiendo jefe y se
configura VITE_DEMO_MANAGER_PASSWORD_SHA256 localmente y en Vercel.

Pregunta: ¿Ocultar el calibrador es seguridad empresarial?
Respuesta: No. Es control visual en el navegador para una demo con imágenes
artificiales. Una solución real debe verificar roles y permisos en un servidor.

Pregunta: ¿Qué sucede al recargar la página?
Respuesta: sessionStorage conserva el rol en esa pestaña. Jefe continúa sin ver
el calibrador y Programador conserva su acceso hasta cerrar sesión.



PREGUNTAS Y RESPUESTAS: PUNTOS INTERACTIVOS CCTV
=================================================

Pregunta: ¿Los puntos representan cámaras reales?
Respuesta: No. Los diez equipos, marcas, modelos, fechas y estados son ficticios.

Pregunta: ¿Por qué el punto desaparece cuando giro?
Respuesta: Está anclado a una posición de la fotografía 360° y solamente se
proyecta cuando esa posición entra en el campo visible de la cámara del usuario.

Pregunta: ¿La ficha muestra las coordenadas de calibración?
Respuesta: No. Yaw y pitch son datos internos del visor y no aportan valor a la
consulta operativa del jefe.

Pregunta: ¿Por qué se muestran instalación y mantenimientos?
Respuesta: Permiten conocer antigüedad, evidencia de revisión y próxima actividad
preventiva, datos importantes para disponibilidad y gestión del activo.

Pregunta: ¿La demo permite ver video en vivo?
Respuesta: No. Representa inventario visual y contexto espacial; no se conecta a
cámaras, grabadores o plataformas VMS.

Pregunta: ¿Programador y Jefe pueden consultar las fichas?
Respuesta: Sí. La diferencia entre roles sigue siendo el calibrador; ambos pueden
recorrer la demo y consultar los puntos CCTV ficticios.



PREGUNTAS Y RESPUESTAS: INGENIEROS, MAPA E HISTORIALES
======================================================

Pregunta: ¿Qué pueden editar los Ingenieros?
Respuesta: Estado, último y próximo mantenimiento, área responsable y
observaciones. Los datos de identidad, diseño y calibración están bloqueados.

Pregunta: ¿Por qué Jefe no puede editar?
Respuesta: Su función en esta demo es supervisar, consultar y auditar. Separar
ejecución y revisión reduce conflictos y mejora la rendición de cuentas.

Pregunta: ¿Orbinodo puede ver los historiales?
Respuesta: No. El requisito reserva los historiales únicamente al Jefe. Orbinodo
conserva el calibrador y el mapa técnico.

Pregunta: ¿El historial dice exactamente quién cambió qué?
Respuesta: Sí. Registra Ingeniero 1 o Ingeniero 2, cámara, fecha, campo, valor
anterior y valor nuevo.

Pregunta: ¿Los cambios se comparten entre computadores?
Respuesta: No en esta demo. localStorage pertenece al navegador. Para compartir
datos se necesita backend y base de datos central.

Pregunta: ¿El historial es evidencia de auditoría empresarial?
Respuesta: No. Puede alterarse o borrarse desde el navegador y usa la hora del
dispositivo. Solo demuestra la experiencia y el flujo esperado.

Pregunta: ¿Por qué el mapa usa colores?
Respuesta: Permite identificar rápidamente equipos operativos, en mantenimiento
o fuera de servicio y priorizar la revisión.

Pregunta: ¿Por qué se muestra el perfil activo?
Respuesta: Reduce el riesgo de editar o presentar la demo desde una cuenta
equivocada y aclara los permisos disponibles.
