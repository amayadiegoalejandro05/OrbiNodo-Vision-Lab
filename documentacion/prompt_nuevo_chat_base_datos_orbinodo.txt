ARQUITECTURA DESEADA PARA LA DEMO LOCAL

Propón e implementa una arquitectura sencilla y mantenible con:

- PostgreSQL instalado y ejecutado en este computador Windows.
- Una API de Orbinodo escrita en Node.js y TypeScript dentro del mismo repositorio,
  separada claramente del frontend.
- Migraciones SQL versionadas.
- Script de datos iniciales para las diez cámaras y los cuatro usuarios de prueba.
- Contraseñas almacenadas con un algoritmo apropiado para contraseñas, como Argon2id
  o bcrypt; no utilizar SHA-256 simple como almacenamiento de contraseñas del servidor.
- Sesiones seguras controladas por el backend. Prefiere cookies HttpOnly y explica
  la configuración necesaria; no guardes tokens sensibles en localStorage.
- Validación de entrada y consultas parametrizadas.
- PostgreSQL accesible únicamente por la API. No publiques el puerto 5432 en internet.
- Operaciones de actualización e historial dentro de una misma transacción SQL, para
  que nunca se guarde el cambio sin su auditoría o viceversa.
- Hora calculada por el servidor/base de datos, no por el reloj del navegador.
- Manejo visible del estado "API no disponible". No vuelvas silenciosamente a
  localStorage, porque eso crearía dos fuentes de verdad diferentes.

QUÉ PASA CUANDO SE APAGA ESTE COMPUTADOR
========================================

La base de datos no debería borrarse al apagar correctamente el computador.
PostgreSQL guarda las tablas en archivos persistentes del SSD. Al volver a encender
el equipo e iniciar PostgreSQL y la API, los datos vuelven a estar disponibles.

Lo que ocurre durante el apagado depende de dónde se aloje cada componente:

CASO 1: PÁGINA EN VERCEL Y API/POSTGRESQL EN ESTE COMPUTADOR

- La dirección de Vercel continúa cargando porque la página está alojada en Vercel.
- La API de Orbinodo queda fuera de servicio mientras el computador esté apagado.
- El inicio de sesión basado en servidor, cámaras compartidas e historiales no
  funcionarán hasta encender nuevamente el computador y levantar los servicios.
- La interfaz debe mostrar "Servidor temporalmente no disponible" y no fingir que
  guardó información localmente.

CASO 2: PÁGINA, API Y POSTGRESQL EN ESTE COMPUTADOR

- La página completa deja de estar disponible mientras el equipo esté apagado.
- Al encenderlo y reiniciar los servicios, la página y los datos vuelven.

LOS DATOS SÍ PODRÍAN PERDERSE SI:

- Se elimina manualmente el directorio de datos de PostgreSQL.
- Se borra el volumen persistente de un contenedor.
- Se usa un comando destructivo como `docker compose down -v`.
- Se desinstala PostgreSQL eliminando también sus datos.
- Falla el SSD y no existe un respaldo válido.
- Una migración o acción administrativa defectuosa modifica o elimina registros.

Por eso se necesitan copias periódicas con pg_dump, una copia en otra unidad física
y una prueba de restauración. Un respaldo que nunca se ha restaurado todavía no debe
considerarse un respaldo comprobado.

APAGADO RECOMENDADO

Se debe cerrar PostgreSQL mediante su servicio o herramienta normal y apagar Windows
correctamente. Un corte eléctrico brusco no equivale a borrar automáticamente la
base; PostgreSQL cuenta con recuperación transaccional, pero los cortes repetidos,
el daño del disco o una escritura interrumpida siguen siendo riesgos. Para una demo
importante conviene utilizar UPS y mantener respaldos recientes.
