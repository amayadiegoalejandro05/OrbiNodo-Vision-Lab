ARQUITECTURA LOCAL DE ORBINODO
==============================

Flujo inicial
-------------

Navegador -> API Node.js y TypeScript -> PostgreSQL 18

El navegador nunca se conecta directamente a PostgreSQL. La API escucha inicialmente
en 127.0.0.1:3001 y PostgreSQL escucha únicamente en localhost:5432. Abrir acceso a
otros dispositivos será una fase posterior que requiere autorización para configurar
HTTPS, firewall y red.

Separación de responsabilidades
-------------------------------

- src contiene el frontend Vite existente.
- backend contiene la API propia de Orbinodo.
- backend/config valida variables de entorno sin publicar secretos.
- backend/database encapsula las conexiones y consultas a PostgreSQL.
- backend/domain contiene contratos independientes de Fastify y PostgreSQL.
- backend/app.ts ensambla endpoints y respuestas HTTP.
- backend/server.ts inicia y detiene ordenadamente el proceso local.

Estado de salud
---------------

GET /api/health consulta CURRENT_TIMESTAMP en PostgreSQL. Si funciona, responde 200
con la hora calculada por el servidor. Si PostgreSQL no está disponible, responde 503
con un mensaje controlado y sin revelar rutas, consultas, contraseñas o trazas.

Fuente de verdad
----------------

La autenticación del frontend ya usa la API. GET /api/cameras lee inventario y estado
operativo desde PostgreSQL. PATCH /api/cameras/:id/operations revalida que el autor
sea Ingeniero 1 o 2, bloquea la fila y guarda estado e historial en una transacción.
El frontend ya carga y edita cámaras mediante esos endpoints. Conserva una copia
solo en memoria para renderizar y vuelve a consultar al recuperar el foco. Si la API
falla muestra el error: no usa localStorage como fuente alternativa de cámaras.

Auditoría central del Jefe
--------------------------

GET /api/audit/access-sessions y GET /api/audit/camera-changes leen directamente
de PostgreSQL. Ambas rutas exigen una sesión válida con rol manager; un Ingeniero
recibe 403 incluso si intenta abrir la URL manualmente. El panel Control del Jefe
consulta las dos rutas cada vez que se abre y agrupa los campos de un mismo guardado.

La vista vista_historial_cambios permite revisar en pgAdmin el Ingeniero, cámara,
código, campo, valor anterior, valor nuevo y fecha local. localStorage ya no participa
en la auditoría usada por la aplicación.

Ejecución en Vercel
-------------------

backend/vercel-handler.ts adapta la misma aplicación Fastify a Vercel Functions. Las
entradas exactas de api/auth, api/cameras y api/audit mantienen todas las rutas /api
en el mismo origen del frontend; api/[...path].ts queda como respaldo. El pool acepta
DATABASE_URL o POSTGRES_URL y normaliza SSL administrado a verify-full.

La Function nunca usa 127.0.0.1 para producción. La producción activa usa Neon,
contiene cuatro migraciones, cuatro usuarios, diez cámaras y cookies Secure. La URL
https://orbinodo-demo.vercel.app fue verificada mediante API y navegador real.

Contrato HTTP cerrado en auditoría
----------------------------------

GET /api/cameras/:id devuelve una cámara autenticada y distingue identificador
inválido (400) de cámara inexistente (404). api/cameras/[id].ts expone esta ruta en
Vercel sin duplicar la aplicación Fastify.

Los errores usan { error, message } con códigos estables para 400, 401, 403, 404,
409, 500 y 503. Los endpoints administrativos no forman parte de v1.0 mientras no
exista un rol administrador y un flujo aprobado; db:reset nunca se publica por HTTP.

El contrato completo de métodos, roles, cuerpos y códigos está en
documentacion/contrato_api_fastify_v1.txt. ORBINODO_TRUSTED_PROXY_HOPS controla de
forma explícita cuántos proxies se confían al calcular request.ip; local usa 0.
