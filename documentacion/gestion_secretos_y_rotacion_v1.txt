GESTION DE SECRETOS Y ROTACION - ORBINODO ENTERPRISE v1.0
=========================================================

REGLAS
------
- No guardar contrasenas, tokens, claves privadas ni DATABASE_URL en codigo,
  documentacion con valores reales, capturas, logs ni repositorio.
- Los archivos .env reales permanecen locales e ignorados por Git. Solo
  .env.example se versiona y contiene valores falsos.
- Las variables VITE_* se consideran publicas: nunca contienen secretos de
  backend, contrasenas, tokens, URL de Neon ni credenciales de proveedores.

MATRIZ DE ENTORNOS
------------------
Desarrollo local:
- .env.backend.local contiene PostgreSQL local y contrasenas de seed.
- .env.local puede contener configuracion visual local, nunca secretos backend.

Preview:
- Vercel almacena DATABASE_URL, ORBINODO_COOKIE_SECURE=true y credenciales de
  prueba en variables de Preview.
- Debe usar una rama, base o rol de Neon distinto de Production.

Production:
- Vercel almacena DATABASE_URL, ORBINODO_COOKIE_SECURE=true y las contrasenas
  locales necesarias solo para verify:production.
- Debe usar el rol y la base de Neon aprobados para produccion.

ROTACION
--------
1. Crear o restablecer la credencial en Neon. No pegarla en chat, Git ni archivos
   documentados.
2. Actualizar DATABASE_URL en Vercel para el entorno afectado.
3. En una consola local, cargar temporalmente la nueva URL y ejecutar:
   npm run db:preflight
4. Desplegar el entorno correspondiente y ejecutar npm run verify:production.
5. Revocar la credencial anterior y registrar fecha, responsable y motivo en el
   sistema corporativo aprobado, no en el repositorio.
6. Rotar inmediatamente ante exposicion, salida de personal o sospecha de uso.

AIR PRODUCTS
------------
Actualmente Air Products no integra servicios con OrbiNodo y no debe proporcionar
secretos. Si se aprueba una integracion futura, seguridad e infraestructura deben
definir por escrito cuales aplican: identidad OIDC o cuenta de servicio, API key,
secreto de firma de webhook, certificado cliente y/o credenciales de almacenamiento.
Cada secreto debe tener propietario, entorno, alcance minimo, fecha de rotacion y
canal de entrega aprobado.

VERIFICACION
------------
- npm run secrets:check revisa archivos rastreados e historial Git alcanzable sin
  imprimir valores detectados.
- npm run build permite revisar que el bundle no use secretos backend.
- npm run verify:production verifica el uso real de la configuracion productiva.
