GUÍA COMPLETA DE FASES DEL RECORRIDO VIRTUAL 360°
===================================================

PROPÓSITO DE ESTE DOCUMENTO

Esta guía explica qué se construye en cada fase, qué se necesita antes de comenzar,
qué resultado debe verse, qué se debe verificar y qué debe comprenderse para
presentar el proyecto. Se actualizará cuando la experiencia real obligue a cambiar
alguna decisión.

REGLA DE AVANCE

Una fase solo se considera terminada cuando:
1. Su resultado visible puede demostrarse.
2. npm run check termina correctamente.
3. Los errores conocidos están documentados.
4. La privacidad de las fotografías se conserva.
5. Las preguntas de defensa de esa fase están actualizadas.
6. Se realizó la revisión manual indicada para esa fase.

-------------------------------------------------------------------------------
FASE 0 — ANÁLISIS Y DISEÑO
-------------------------------------------------------------------------------

Objetivo:
Entender el problema y elegir una solución proporcional antes de escribir código.

Requiere:
Descripción de la vivienda, cantidad aproximada de fotos, herramientas disponibles
y restricciones de privacidad.

Actividades:
- Inspeccionar la carpeta, Git, Node.js, npm y Visual Studio Code.
- Comparar lenguajes, frameworks y visores 360°.
- Definir arquitectura, modelo de datos, navegación y estrategia de imágenes.
- Separar el alcance actual de las ampliaciones futuras.
- Identificar riesgos de memoria, WebGL, orientación y privacidad.

Resultado:
Un plan técnico justificable: TypeScript, Vite, Photo Sphere Viewer, aplicación
estática local y configuración independiente del visor.

Debe comprenderse:
Qué es una aplicación estática, por qué no se necesita backend y por qué una
fotografía equirectangular representa una esfera.

Criterio de cierre:
Las decisiones principales tienen alternativas, consecuencias y justificación.

FASE 1 — PROYECTO MÍNIMO
-------------------------------------------------------------------------------

Objetivo:
Crear una base ejecutable antes de integrar WebGL o fotografías.

Requiere:
Node.js, npm, Visual Studio Code y autorización para instalar dependencias.

Actividades:
- Inicializar Vite con TypeScript.
- Configurar ESLint y comprobación estricta de tipos.
- Crear HTML semántico y estilos adaptables.
- Inicializar Git local y las exclusiones de privacidad.
- Crear comandos, documentación y banco de preguntas.

Resultado:
Una página local funcional que confirma que HTML, CSS y TypeScript se conectan.

Verificación:
npm run check y respuesta HTTP local.

Debe comprenderse:
index.html inicia la página, main.ts ejecuta la lógica, CSS presenta la interfaz,
package.json define comandos y package-lock.json fija versiones.

Criterio de cierre:
La página responde, cambia su estado mediante TypeScript y se construye en dist.

-------------------------------------------------------------------------------
FASE 2 — PANORAMA INDIVIDUAL
-------------------------------------------------------------------------------

Objetivo:
Mostrar una imagen equirectangular completa dentro de un visor interactivo.

Requiere:
- Photo Sphere Viewer y su dependencia Three.js.
- Una imagen 2:1, 360° × 180°, sin información privada.
- Navegador moderno con WebGL.

Actividades:
- Crear un adaptador aislado para Photo Sphere Viewer.
- Cargar un panorama de demostración local.
- Habilitar arrastre, zoom, controles y pantalla completa.
- Mostrar progreso, estado listo y errores comprensibles.
- Ofrecer reintento cuando la imagen falla.
- Liberar recursos WebGL al cerrar la página.
- Adaptar el área panorámica a computador y teléfono.

Resultado:
El parqueadero ficticio puede observarse en todas direcciones y ampliarse.

Verificación automática:
Tipos, ESLint, build, respuesta HTTP y disponibilidad HTTP de la imagen.

Verificación manual:
Arrastrar, zoom con rueda, botones +/−, pantalla completa, pellizco táctil y cambio
de orientación del teléfono.

Debe comprenderse:
La biblioteca coloca la textura dentro de una esfera; la cámara permanece en el
centro. Nuestro código controla estados y mensajes, mientras la biblioteca dibuja.

Limitación:
Solo existe un panorama; todavía no hay conexiones ni habitaciones navegables.
El paquete del visor aumenta el JavaScript porque incluye Three.js. Se medirá y
optimizará en la fase de experiencia completa.

Criterio de cierre:
La imagen carga localmente, puede girarse y ampliarse, y existe manejo de errores.

-------------------------------------------------------------------------------
FASE 3 — RECORRIDO MÍNIMO
-------------------------------------------------------------------------------

Objetivo:
Demostrar navegación espacial entre Parqueadero, Pasillo y Cocina.

Requiere:
Tres panoramas sintéticos 2:1 y una primera versión del modelo de datos.

Actividades:
- Instalar el Virtual Tour Plugin.
- Definir tipos para panorama, conexión y vista inicial.
- Crear identificadores estables.
- Declarar conexiones explícitas de ida y regreso.
- Posicionar flechas con yaw y pitch.
- Validar destinos, duplicados e inicio.
- Actualizar la ubicación cuando cambia el panorama.

Resultado:
Parqueadero ↔ Pasillo ↔ Cocina con transiciones comprensibles.

Verificación:
Pruebas del validador, navegación manual en ambos sentidos y build.

Debe comprenderse:
Una conexión es dirigida. El regreso se declara aparte porque su flecha tiene otra
orientación dentro de la fotografía de destino.

Criterio de cierre:
Los tres puntos pueden recorrerse y ninguna conexión apunta a un id inexistente.

FASE 4 — NAVEGACIÓN DIRECTA
-------------------------------------------------------------------------------

Objetivo:
Permitir saltar a una habitación sin recorrer todos los puntos anteriores.

Requiere:
Modelo con pisos, habitaciones y panorama representativo.

Actividades:
- Crear menú agrupado por piso.
- Definir entryPanoramaId para cada habitación.
- Sincronizar menú, visor y ubicación actual.
- Activar el botón de inicio.
- Manejar habitación o panorama inexistente.
- Añadir navegación básica por teclado al menú.

Resultado:
El usuario puede elegir Parqueadero, Pasillo o Cocina directamente y sabe dónde está.

Verificación:
Pruebas de navegación directa, estado actual y errores controlados.

Debe comprenderse:
El menú no contiene rutas duplicadas; se genera desde la misma configuración usada
por el visor.

Criterio de cierre:
Cada habitación registrada abre exactamente su panorama representativo.

FASE 6 — DEMO PÚBLICA CON ACCESO BÁSICO
-------------------------------------------------------------------------------

Objetivo:
Publicar Orbinodo en una URL HTTPS accesible desde cualquier computador o teléfono,
sin depender de localhost ni de la misma red Wi-Fi. Antes de mostrar el recorrido,
la página solicitará un usuario y una contraseña de demostración.

Alcance aceptado:
- La página y las panorámicas artificiales serán recursos públicos.
- El acceso será una barrera visual y práctica para una presentación.
- No se pretende proteger información sensible.
- Una persona con conocimientos técnicos podría inspeccionar el JavaScript, abrir
  directamente un archivo público o modificar el estado del navegador.
- Nunca se reutilizará una contraseña personal, bancaria, laboral o de correo.

Decisión técnica:
- Vercel alojará la aplicación Vite y entregará una URL HTTPS pública.
- No se utilizarán Supabase, base de datos, backend ni almacenamiento privado.
- El usuario se configurará con VITE_DEMO_USERNAME.
- La contraseña no se guardará como texto visible; se comparará su SHA-256 mediante
  Web Crypto con VITE_DEMO_PASSWORD_SHA256.
- Ambas variables VITE terminan dentro del paquete público. El hash evita texto plano,
  pero no convierte la solución en autenticación segura.
- sessionStorage conservará el acceso durante la pestaña actual.
- Un botón Cerrar sesión borrará el estado y volverá a la pantalla de ingreso.

Qué se debe instalar:
- npm install --save-dev vercel
No se necesita instalar @supabase/supabase-js ni crear una base de datos.

Archivos y módulos previstos:
- .env.example: nombres de VITE_DEMO_USERNAME y VITE_DEMO_PASSWORD_SHA256 sin valores.
- .env.local: valores de desarrollo, ignorados por Git.
- src/auth/demo-auth.ts: comparación del usuario y hash de la contraseña.
- src/auth/login-view.ts: formulario, errores, estado de espera y accesibilidad.
- scripts/hash-demo-password.mjs: genera el hash sin guardar la contraseña en código.
- vercel.json: configuración de la aplicación SPA y encabezado noindex si se decide.
- index.html y main.ts: pantalla de ingreso, guardia de inicio y cierre de sesión.
- main.css: diseño del acceso para computador y teléfono.

Experiencia prevista:
1. La persona abre la URL pública.
2. Ve el nombre Orbinodo y el formulario de acceso.
3. Introduce el usuario y la contraseña de demostración.
4. Si son válidos, se monta el recorrido virtual.
5. Si son incorrectos, aparece un mensaje genérico.
6. Cerrar sesión destruye el visor y regresa al formulario.
7. Cerrar la pestaña elimina la sesión temporal.

Actividades:
1. Crear el formulario accesible de usuario y contraseña.
2. Crear el generador local de SHA-256.
3. Comparar credenciales sin almacenar la contraseña en texto plano.
4. Evitar que el recorrido y WebGL se inicialicen antes de ingresar.
5. Añadir cierre de sesión y limpiar sessionStorage.
6. Añadir espera breve después de varios intentos fallidos como mejora de experiencia.
7. Añadir .env.example sin valores reales y confirmar que .env.local sigue ignorado.
8. Añadir vercel.json para la SPA.
9. Instalar la CLI de Vercel.
10. Ejecutar npm run check antes de publicar.
11. Crear primero una vista previa con npx vercel.
12. Probar la vista previa desde otro computador y desde datos móviles.
13. Después de aprobarla, ejecutar npx vercel --prod.
14. Cambiar o retirar las credenciales al terminar la demostración.

Usuario y contraseña:
- El propietario elegirá un usuario de demostración.
- El propietario elegirá una contraseña exclusiva para esta demo.
- La contraseña no debe enviarse por chat ni añadirse a los TXT.
- El hash se generará localmente y se configurará en Vercel.
- Cambiar usuario o hash requiere un nuevo despliegue.

Medidas básicas:
- HTTPS proporcionado por Vercel.
- Contraseña exclusiva y desechable.
- Comparación mediante hash, no texto plano.
- Mensaje genérico para credenciales incorrectas.
- sessionStorage en lugar de una sesión permanente.
- Botón visible para cerrar sesión.
- Etiqueta noindex para reducir indexación accidental.
- No publicar fotografías reales bajo este modelo sin revisar nuevamente la seguridad.

Verificación:
- La URL abre desde una red diferente.
- Sin iniciar sesión solo se ve el formulario.
- Usuario o contraseña incorrectos no montan el visor.
- Las credenciales correctas abren Orbinodo.
- Recargar conserva la sesión dentro de la pestaña.
- Cerrar sesión oculta el recorrido y libera WebGL.
- Cerrar la pestaña elimina el acceso temporal.
- El formulario funciona con teclado y en pantalla móvil.
- Los ocho panoramas y las nueve rutas verificadas siguen funcionando.
- npm run check termina correctamente.
- La vista previa se aprueba antes de producción.

Criterio de cierre:
La persona recibe una URL pública, escribe las credenciales de demostración y entra a
Orbinodo desde cualquier red. La limitación de seguridad queda comprendida y no se
usa esta solución para fotografías o datos sensibles.

Publicación y autorización:
Crear una vista previa o producción cambia un servicio externo. No se ejecutará
npx vercel ni se compartirá una URL sin autorización explícita del propietario.

Fuente oficial de alojamiento:
- https://vercel.com/docs/frameworks/frontend/vite

HERRAMIENTAS DEL PROYECTO Y POR QUÉ SE UTILIZAN
-------------------------------------------------------------------------------

Visual Studio Code:
Es el editor principal. Permite navegar archivos, ejecutar terminales, detectar
errores de TypeScript y usar extensiones. No es necesario para que el recorrido
funcione en el navegador, pero facilita desarrollarlo y explicarlo.

HTML:
Define la estructura y el significado de la página: cabecera, ubicación, menú,
contenedor panorámico, estados y botones. Se eligió porque es el lenguaje nativo
de estructura en la web y permite accesibilidad mediante etiquetas y atributos ARIA.

CSS:
Controla colores, tamaños, distribución y adaptación móvil. Se mantiene separado de
la lógica para modificar el aspecto sin alterar la navegación.

JavaScript:
Es el lenguaje que ejecutan los navegadores. El proyecto final siempre termina
ejecutando JavaScript, aunque el código fuente se escriba en TypeScript.

TypeScript:
Añade tipos y comprobaciones antes de ejecutar. Detecta selectores posiblemente
nulos, propiedades equivocadas y contratos inconsistentes. Resulta especialmente
útil cuando la configuración crezca a unos cuarenta panoramas.

Node.js:
Ejecuta las herramientas de desarrollo como Vite, TypeScript y ESLint. No se utiliza
como backend ni recibe fotografías durante el recorrido.

npm:
Instala dependencias y ejecuta los scripts de package.json. package-lock.json fija
las versiones exactas para reproducir la instalación en otro computador.

Vite:
Inicia el servidor local, transforma TypeScript y CSS y genera dist. Se eligió por
su configuración pequeña y porque la aplicación es un sitio estático, no un servidor
con base de datos.

Photo Sphere Viewer:
Convierte una imagen equirectangular en una experiencia 360°. Proporciona WebGL,
arrastre, zoom, controles, pantalla completa y eventos. Evita reconstruir un motor
panorámico desde cero.

Three.js:
Es una dependencia interna de Photo Sphere Viewer. Se encarga de gráficos 3D y
comunicación con WebGL. Nuestro código no la utiliza directamente para reducir
acoplamiento y complejidad.

WebGL:
Es la API del navegador que utiliza la GPU para dibujar la esfera y la textura.
Puede fallar si el navegador, controlador gráfico o dispositivo no lo soportan.

ESLint:
Analiza el código sin ejecutarlo. Busca patrones problemáticos y mantiene reglas
consistentes. No reemplaza las pruebas ni la comprobación de tipos.

typescript-eslint:
Permite que ESLint comprenda la sintaxis de TypeScript y aplique reglas específicas.

Git:
Guarda el historial local del código y la documentación. No implica publicar en
Internet. Las fotografías privadas se excluyen antes de cualquier commit.

Vitest, previsto desde la Fase 3:
Automatizará validaciones del modelo, conexiones e identificadores. Comparte la
infraestructura de Vite y es proporcional al tamaño del proyecto.

Virtual Tour Plugin, previsto desde la Fase 3:
Añadirá nodos, enlaces y flechas entre panoramas. No se instaló en Fase 2 porque un
solo panorama no necesita navegación espacial.

Mosaicos equirectangulares, opción de Fase 7:
Dividen fotografías muy grandes para cargar únicamente las regiones necesarias.
Solo se incorporarán si las mediciones con imágenes reales justifican la complejidad.

ACTUALIZACIÓN DE FASE 6 — IMPLEMENTACIÓN LOCAL COMPLETADA

Objetivo alcanzado
Se añadió una pantalla de acceso antes del recorrido. El visor panorámico no se crea hasta que el usuario y la contraseña son correctos. La sesión vive en sessionStorage: resiste una recarga de la misma pestaña, pero desaparece al cerrar la pestaña o al pulsar Cerrar sesión.

Qué se implementó
- Formulario accesible y adaptable a celular.
- Usuario configurable mediante VITE_DEMO_USERNAME.
- Contraseña comparada mediante un hash SHA-256 configurado en VITE_DEMO_PASSWORD_SHA256.
- Creación diferida del visor y destrucción de sus recursos al cerrar sesión.
- Archivo .env.example sin credenciales reales y .env.local ignorado por Git.
- Comando interactivo npm run auth:hash para producir el hash sin escribir la contraseña en el comando.
- Configuración vercel.json para construir con Vite y publicar dist.
- Pruebas unitarias y prueba real en Edge de rechazo, acceso, recarga, cierre de sesión y diseño móvil.

Por qué fue necesario
La demostración será accesible desde Internet. Esta barrera evita que una visita casual vea inmediatamente el recorrido y permite entregar credenciales al destinatario. No es seguridad fuerte: Vite incorpora las variables al JavaScript del navegador y las imágenes artificiales continuarán siendo archivos públicos. Para fotografías privadas reales se requerirá autenticación de servidor y almacenamiento privado en otra fase.

Estado y criterio de aceptación
Fase 6 local completada. npm run check aprobó ESLint, 9 pruebas, TypeScript, compilación y verificación en Edge sin errores. Queda pendiente únicamente la publicación externa, que se realizará después de configurar en Vercel el mismo usuario y hash y obtener autorización expresa.

Pasos restantes fuera del entorno local
1. Elegir las credenciales definitivas y generar el hash localmente.
2. Probarlas en .env.local.
3. Iniciar sesión en Vercel.
4. Crear el proyecto de vista previa.
5. Registrar ambas variables para Preview y Production.
6. desplegar una vista previa y comprobarla desde otra red.
7. Publicar en producción solo después de aprobar la vista previa.

AVANCE DE FASE 7 — MINIMAPA INTERACTIVO

Se añadió un minimapa lógico y sencillo con diez nodos agrupados por las cuatro zonas del recorrido. Cian significa ubicación disponible y naranja significa ubicación actual. Al tocar un nodo, el visor se transporta directamente al panorama asociado.

El minimapa se genera desde los mismos datos del recorrido; por ello, un panorama nuevo aparecerá automáticamente cuando se agregue correctamente a TourConfig. No debe interpretarse como plano arquitectónico ni como representación a escala.

MEJORA DE LA FASE 7: MINIMAPA TIPO VIDEOJUEGO Y FLECHAS DIRECCIONALES
=======================================================================

Qué se cambió
-------------

El minimapa de nodos dejó de estar dentro del menú lateral. Ahora se muestra
como una interfaz superpuesta o HUD en la esquina inferior derecha del recorrido
360°. De esta manera la referencia espacial permanece visible mientras el
usuario observa el inmueble, tanto en computador como en celular.

El mapa continúa siendo lógico: cada punto representa una ubicación navegable,
el color naranja identifica el panorama actual y el cian identifica los demás.
Tocar un nodo sigue transportando directamente al espacio correspondiente.

También se cambió el renderizado de las flechas de navegación. Antes se usaba
el modo de suelo 3D, que favorecía una fila de flechas en la parte inferior y no
aprovechaba completamente el pitch calibrado. Ahora cada flecha está anclada a
su yaw y pitch dentro de la esfera panorámica. Una flecha solamente entra en
pantalla cuando el usuario gira hacia la puerta, escalera o zona de paso donde
fue calibrada. Esto reduce confusiones entre destinos ubicados en direcciones
diferentes.

Evolución futura: plano arquitectónico con nodos
------------------------------------------------

Sí es posible reemplazar el fondo lógico por el plano real de cada planta y
conservar los nodos interactivos sobre las habitaciones correspondientes. Para
esa evolución se requerirá:

1. Un plano por nivel, preferiblemente SVG por su nitidez y facilidad de escala;
   también puede utilizarse PNG si el plano ya está disponible como imagen.
2. Una posición X/Y de mapa para cada panorama. Estas coordenadas son distintas
   de yaw y pitch: X/Y ubica el punto sobre la planta; yaw/pitch ubica una flecha
   dentro de la fotografía 360°.
3. Un selector de planta para mostrar Sótano, Primer piso, Segundo piso y
   Exterior sin mezclar nodos de niveles diferentes.
4. Una marca naranja para la ubicación actual y, opcionalmente, un cono o
   indicador de orientación que muestre hacia dónde está mirando el usuario.
5. Planos revisados para no publicar información sensible cuando se usen
   instalaciones reales de una empresa.

La estructura actual no se desperdicia. Los identificadores de panorama, la
navegación por nodos y el cambio directo de ubicación ya están preparados. En
una fase futura se añadirían el archivo del plano y las coordenadas X/Y de cada
nodo; no sería necesario reconstruir el recorrido completo.

Comprobaciones realizadas
-------------------------

- TypeScript terminó sin errores.
- Las 10 pruebas unitarias terminaron correctamente.
- Edge comprobó 10 nodos, minimapa dentro de la zona inferior del recorrido,
  una sola flecha dentro de la mirada inicial, navegación al Jardín, recarga,
  vista móvil y cierre de sesión, sin errores de navegador.



CORRECCIÓN DE LA MEJORA DE FASE 7: MAPA LATERAL Y FLECHAS DE SUELO
==================================================================

Decisión vigente
----------------

La propuesta de mostrar el minimapa como HUD encima del panorama fue probada,
pero se decidió aplazarla porque ocupaba demasiado espacio de la imagen,
especialmente en celular. El minimapa de nodos volvió al panel lateral con el
tamaño y la distribución que tenía antes. La idea del plano arquitectónico se
conserva como una posible mejora futura, sujeta a aprobación.

Las flechas también regresaron al modo de suelo 3D. Este modo las muestra
recostadas en la parte inferior y evita que parezcan apuntar hacia arriba o que
interfieran con la vista frontal de puertas, paredes y otros elementos.

Se conservó una mejora del intento anterior: no se muestran todas las flechas
del suelo simultáneamente. El sistema compara el yaw de cada enlace con la
dirección actual de la cámara y con el campo de visión horizontal. Una flecha
queda visible solamente cuando su dirección está dentro de la mirada del
usuario. Las demás se ocultan y no aceptan clics hasta que el usuario gira hacia
ellas.

La posición vertical visual de una flecha vuelve a ser controlada por el modo de
suelo 3D. Los valores yaw siguen determinando la dirección de cada destino. Los
valores pitch permanecen guardados en los datos y podrán reutilizarse si en el
futuro se decide volver a marcadores anclados directamente a la fotografía.

Resultado verificado
--------------------

- El minimapa contiene 10 nodos y pertenece al panel lateral.
- En Parqueadero se crean dos flechas de suelo, una por cada destino.
- En la mirada inicial solamente una de esas dos flechas está visible.
- La navegación al Jardín, la versión móvil, la recarga y el cierre de sesión
  continúan funcionando sin errores.



CORRECCIÓN: LAS FLECHAS SE VEÍAN PERO NO ACEPTABAN CLICS
=========================================================

Problema encontrado
-------------------

Después de agregar el filtro direccional, la flecha correcta se veía sobre el
suelo, pero no permitía navegar. El contenedor 3D del complemento utiliza
pointer-events: none para que las zonas vacías de su capa no bloqueen el giro
del panorama. Cada flecha interactiva debe habilitar sus propios eventos.

Al volver a mostrar una flecha, el filtro anterior dejaba pointer-events sin un
valor explícito. Por herencia práctica de la capa 3D, la flecha quedaba visible
pero el clic atravesaba el elemento y llegaba al panorama.

Corrección aplicada
-------------------

Las flechas fuera de cámara continúan usando pointer-events: none. Las flechas
dentro de la mirada ahora recuperan explícitamente pointer-events: auto. Esto
permite hacer clic para avanzar y regresar sin impedir que el usuario arrastre
el panorama en las demás zonas de la imagen.

La prueba de navegador también fue mejorada. Ya no se limita a comprobar que la
flecha exista y sea visible: hace un clic normal, sin forzar la acción, y exige
que el recorrido cambie de Parqueadero a Pasillo. Así, una futura pérdida de
interactividad será detectada automáticamente.

Resultado: TypeScript correcto, 10 pruebas unitarias aprobadas y navegación
manual Parqueadero -> Pasillo confirmada en Edge, sin errores de navegador.



MEJORA DE FASE 7: DOS USUARIOS CON ROLES PROGRAMADOR Y JEFE
============================================================

Objetivo
--------

La demo ahora distingue dos tipos de acceso:

- Programador: puede recorrer todos los espacios y dispone del botón del
  calibrador yaw/pitch, la mira central, la lectura de coordenadas y la copia.
- Jefe: puede recorrer exactamente los mismos espacios, usar flechas, menú y
  minimapa, pero no ve ninguna herramienta de calibración.

Configuración vigente
---------------------

La cuenta que ya existía mediante VITE_DEMO_USERNAME y
VITE_DEMO_PASSWORD_SHA256 pasa a ser la cuenta de Programador. No es necesario
cambiar sus credenciales locales para conservar el acceso actual.

La cuenta de Jefe utiliza estas variables opcionales:

VITE_DEMO_MANAGER_USERNAME
VITE_DEMO_MANAGER_PASSWORD_SHA256

Si todavía no se añaden, el sistema habilita temporalmente el usuario Jefe con
la misma contraseña configurada para Programador. Esto permite probar los dos
roles inmediatamente sin revelar ni reemplazar la contraseña existente.

Para separar también las contraseñas, se debe ejecutar npm run auth:hash, elegir
el rol jefe y agregar el hash resultante a .env.local y posteriormente a Vercel.
El texto real de la contraseña no debe guardarse en código ni documentación.

Funcionamiento de la sesión
---------------------------

Después de validar las credenciales, sessionStorage guarda programmer o manager.
Al recargar la pestaña, el sistema recupera el rol y vuelve a aplicar la interfaz
correcta. Al cerrar sesión elimina el rol. Las sesiones antiguas que solamente
guardaban true dejan de ser aceptadas porque no permiten determinar permisos.

Ocultamiento del calibrador
---------------------------

La aplicación aplica el rol antes de mostrar el recorrido. Para Jefe se oculta
la barra completa, se desactiva cualquier calibración que hubiera quedado
abierta y también se oculta la mira. Esto evita un destello momentáneo del botón
durante la carga o después de cambiar de usuario.

Limitación de seguridad
-----------------------

Esta separación es apropiada para la demo con panoramas artificiales, pero no es
control de acceso empresarial. Las variables VITE y la decisión del rol se
ejecutan en el navegador; una persona con conocimientos técnicos podría alterar
la interfaz. Para fotografías reales o información sensible se requerirían
autenticación de servidor, permisos verificados en backend y almacenamiento
privado.

Resultado verificado
--------------------

- Programador ve y puede activar el calibrador.
- Jefe no ve botón, barra, lecturas ni mira.
- La recarga conserva correctamente la sesión de Jefe sin mostrar el calibrador.
- 11 pruebas unitarias y la prueba integral de Edge terminaron sin errores.
- Flechas, minimapa, navegación manual, celular y cierre de sesión continúan
  funcionando.



MEJORA DE FASE 7: PUNTOS INTERACTIVOS DE CÁMARAS CCTV
=====================================================

Se agregaron diez cámaras ficticias, una por panorama. Nueve son de tipo 360° y
la cámara del Pasillo es fija. Cada punto utiliza el yaw y pitch suministrados,
pero esas coordenadas no aparecen en la ficha visible.

Los puntos son proyectados por MarkersPlugin dentro de la esfera panorámica. Se
muestran únicamente cuando entran en la vista del usuario y desaparecen al girar
hacia otra dirección. Al tocarlos abren una ficha lateral con nombre, lugar,
código de activo, marca y modelo ficticios, tipo, estado, cobertura, grabación,
retención, instalación, mantenimiento, próxima revisión, responsable y notas.

La documentación detallada, la pertinencia de cada dato y los diez registros se
encuentran en documentacion/puntos_interactivos_camaras_cctv.txt.

Esta función representa inventario visual para seguridad patrimonial. No conecta
cámaras reales, no transmite video y no sustituye un VMS. La implementación local
pasó TypeScript, 14 pruebas unitarias y la verificación integral en Edge.



MEJORA DE FASE 7: CUATRO PERFILES, EDICIÓN Y AUDITORÍA SIMULADA
===============================================================

Se agregaron Ingeniero 1 e Ingeniero 2. Ambos pueden consultar el mapa de diez
cámaras y editar únicamente estado operativo, último mantenimiento, próximo
mantenimiento, área responsable y observaciones. Identidad, equipo, diseño y
coordenadas permanecen bloqueados.

Orbinodo conserva el calibrador y recibe también el mapa como herramienta para
localizar los equipos que en el futuro podrían recalibrarse o ampliarse. Jefe no
ve el calibrador, consulta fichas de solo lectura y dispone de dos historiales:
accesos exitosos y cambios explícitos de ingeniería con valores anterior/nuevo.

Se añadieron indicador de perfil, estados por color, validación de fechas y límite
de 200 entradas por historial. Estas funciones reducen errores operativos y hacen
la trazabilidad más comprensible durante la demostración.

La persistencia usa localStorage. Los cambios solamente se comparten entre los
perfiles que ingresan en el mismo navegador y pueden alterarse con herramientas
del cliente. Es una simulación funcional, no auditoría empresarial. El detalle
completo está en documentacion/perfiles_permisos_edicion_e_historiales.txt.

FASE 8 - BASE DE DATOS CENTRAL PROPIA
=====================================

Paso 1: instalación y aislamiento local
---------------------------------------

PostgreSQL 18.6 quedó instalado como servicio automático. Escucha solo en
127.0.0.1 y ::1; el puerto 5432 no está publicado en la red. Se crearon la base
orbinodo_demo y el usuario técnico no administrador orbinodo_api.

Paso 2: API y migraciones iniciales
-----------------------------------

El backend TypeScript vive en backend y expone GET /api/health. La migración
0001 crea users, cameras, camera_operational_state, camera_change_history y
access_sessions. El runner usa checksums, bloqueo asesor, consultas parametrizadas
y una transacción completa. Todavía faltan seed, autenticación y migración del
frontend; por ahora localStorage sigue activo únicamente como estado anterior.

Paso 3: datos iniciales seguros
-------------------------------

El comando db:seed toma cuatro contraseñas únicamente de .env.backend.local y usa
Argon2id de Node.js con salt aleatorio. Crea Orbinodo, Jefe, Ingeniero 1 e Ingeniero 2
y carga las diez cámaras ficticias. La ejecución es transaccional e idempotente: no
duplica filas ni reemplaza estados operativos que ya existan.
