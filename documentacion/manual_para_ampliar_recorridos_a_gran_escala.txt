ORBINODO — MANUAL PARA AGREGAR ESPACIOS Y ESCALAR RECORRIDOS
================================================================

PROPÓSITO DEL DOCUMENTO

Este manual explica cómo ampliar el recorrido actual con más pisos, ambientes y puntos panorámicos sin romper la navegación. También define una convención de nombres y una arquitectura futura para administrar múltiples instalaciones a gran escala.

Por el momento se utilizarán únicamente imágenes artificiales. Las recomendaciones sobre almacenamiento privado se dejan como preparación futura, no como requisito de la demo actual.

-------------------------------------------------------------------------------
1. CÓMO ESTÁ ORGANIZADO EL RECORRIDO ACTUAL
-------------------------------------------------------------------------------

El recorrido se define en:

src/data/demo-tour.ts

Su estructura jerárquica es:

Recorrido
  └── Pisos
       └── Ambientes o espacios
            └── Panoramas o puntos 360°
                 └── Enlaces hacia otros panoramas

Los tipos se encuentran en:

src/domain/tour.types.ts

TourConfig contiene:
- title: nombre visible del recorrido.
- startPanoramaId: panorama que se abre al iniciar.
- floors: lista ordenada de pisos.

TourFloor contiene:
- id: identificador interno único.
- name: nombre visible para el usuario.
- rooms: ambientes pertenecientes al piso.

TourRoom contiene:
- id: identificador interno único en todo el recorrido.
- name: nombre visible del ambiente.
- entryPanoramaId: punto que se abre al seleccionar el ambiente en el menú.
- panoramas: uno o varios puntos 360° del ambiente.

TourPanorama contiene:
- id: identificador interno único en todo el recorrido.
- name: nombre visible del punto.
- image: ruta de la imagen dentro de public.
- links: conexiones que aparecen como flechas.

TourLink contiene:
- targetId: panorama de destino.
- label: descripción accesible de la acción.
- yaw: dirección horizontal de la flecha.
- pitch: inclinación vertical de la flecha.

-------------------------------------------------------------------------------
2. DIFERENCIA ENTRE AMBIENTE Y PANORAMA
-------------------------------------------------------------------------------

Un ambiente representa una zona que el usuario reconoce, por ejemplo:

- Portería
- Recepción
- Cuarto de control
- Pasillo norte
- Almacén
- Escalera occidental

Un panorama representa un punto exacto desde el cual se observa en 360°. Un ambiente pequeño puede tener un panorama. Un ambiente grande puede tener varios.

Ejemplo:

Ambiente: Almacén principal
  - Punto 1: Entrada
  - Punto 2: Centro
  - Punto 3: Fondo

El menú abre entryPanoramaId, normalmente el punto de entrada. Desde allí las flechas permiten recorrer los demás puntos.

No se debe crear un ambiente nuevo solo porque hay otra posición de cámara dentro del mismo lugar. Debe crearse otro panorama dentro del ambiente existente.

-------------------------------------------------------------------------------
3. CONVENCIÓN DE NOMBRES RECOMENDADA
-------------------------------------------------------------------------------

Los nombres visibles pueden contener espacios, tildes y mayúsculas. Los id y archivos deben usar minúsculas, números y guiones.

Reglas para id:
- Usar minúsculas.
- Separar palabras con guion medio.
- No usar espacios, tildes, eñes ni caracteres especiales.
- No reutilizar un id en otro piso o ambiente.
- Mantener una longitud razonable y un significado estable.
- No incluir información confidencial en el nombre del archivo.

Para una sola instalación pequeña:

Piso:
piso-01
piso-02
sotano-01
exterior

Ambiente:
p01-recepcion
p01-pasillo-norte
p02-cuarto-control
ext-porteria

Panorama:
p01-recepcion-001
p01-recepcion-002
p02-cuarto-control-001

Archivo:
p01-recepcion-001.png
p01-recepcion-002.png

Para múltiples instalaciones se recomienda incluir un código de sede:

Código de instalación:
co-ctg-planta-01

Panorama:
co-ctg-planta-01-p01-recepcion-001

Archivo:
co-ctg-planta-01-p01-recepcion-001.png

La convención puede interpretarse así:

co             país
ctg            ciudad o región
planta-01      instalación
p01            piso o nivel
recepcion      ambiente
001            punto panorámico

El código debe ser acordado con la empresa. No conviene utilizar nombres que revelen públicamente ubicaciones sensibles. En una versión empresarial, el identificador público puede ser opaco y el nombre descriptivo puede vivir en una base de datos protegida.

-------------------------------------------------------------------------------
4. CÓMO PREPARAR UNA IMAGEN ARTIFICIAL
-------------------------------------------------------------------------------

Para la demo, cada panorama debe cumplir:

- Proyección equirectangular.
- Relación de aspecto 2:1.
- Horizonte nivelado.
- Formato PNG, JPG o WebP compatible con el navegador.
- Orientación coherente con las conexiones.
- Nombre igual a la convención del panorama.

Ejemplos de dimensiones 2:1:

2048 x 1024
4096 x 2048
6000 x 3000

Una imagen 360° no debe deformarse para forzar la relación 2:1. Debe generarse o exportarse correctamente como equirectangular.

Ubicación actual de imágenes artificiales:

public/panoramas/demo/

Ejemplo:

public/panoramas/demo/p01-recepcion-001.png

La propiedad image no comienza con public ni con una barra:

image: 'panoramas/demo/p01-recepcion-001.png'

El validador rechaza rutas externas, rutas vacías y rutas con .. por seguridad y consistencia.

-------------------------------------------------------------------------------
5. CÓMO AGREGAR UN AMBIENTE CON UN SOLO PANORAMA
-------------------------------------------------------------------------------

Ejemplo: agregar Recepción en el primer piso.

Paso 1. Copiar la imagen artificial:

public/panoramas/demo/p01-recepcion-001.png

Paso 2. Agregar el ambiente dentro de rooms del piso correspondiente:

{
  id: 'p01-recepcion',
  name: 'Recepción',
  entryPanoramaId: 'p01-recepcion-001',
  panoramas: [
    {
      id: 'p01-recepcion-001',
      name: 'Entrada',
      image: 'panoramas/demo/p01-recepcion-001.png',
      links: [
        {
          targetId: 'p01-pasillo-001',
          label: 'Ir al pasillo',
          yaw: 30,
          pitch: -10,
        },
      ],
    },
  ],
}

Paso 3. Agregar el enlace de regreso en p01-pasillo-001:

{
  targetId: 'p01-recepcion-001',
  label: 'Ir a recepción',
  yaw: -150,
  pitch: -10,
}

Paso 4. Ejecutar:

npm run check

El ambiente aparecerá automáticamente en el menú porque location-menu.ts genera la interfaz desde TourConfig. No se debe escribir otro botón manualmente en index.html.

-------------------------------------------------------------------------------
6. CÓMO AGREGAR VARIOS PUNTOS EN UN MISMO AMBIENTE
-------------------------------------------------------------------------------

Ejemplo: Almacén principal con tres puntos.

{
  id: 'p01-almacen-principal',
  name: 'Almacén principal',
  entryPanoramaId: 'p01-almacen-principal-001',
  panoramas: [
    {
      id: 'p01-almacen-principal-001',
      name: 'Entrada',
      image: 'panoramas/demo/p01-almacen-principal-001.png',
      links: [
        { targetId: 'p01-pasillo-001', label: 'Volver al pasillo', yaw: 180, pitch: -10 },
        { targetId: 'p01-almacen-principal-002', label: 'Avanzar al centro', yaw: 0, pitch: -10 },
      ],
    },
    {
      id: 'p01-almacen-principal-002',
      name: 'Centro',
      image: 'panoramas/demo/p01-almacen-principal-002.png',
      links: [
        { targetId: 'p01-almacen-principal-001', label: 'Volver a la entrada', yaw: 180, pitch: -10 },
        { targetId: 'p01-almacen-principal-003', label: 'Avanzar al fondo', yaw: 0, pitch: -10 },
      ],
    },
    {
      id: 'p01-almacen-principal-003',
      name: 'Fondo',
      image: 'panoramas/demo/p01-almacen-principal-003.png',
      links: [
        { targetId: 'p01-almacen-principal-002', label: 'Volver al centro', yaw: 180, pitch: -10 },
      ],
    },
  ],
}

El menú mostrará una entrada llamada Almacén principal y abrirá el punto 001. Los puntos 002 y 003 se recorren mediante flechas.

Todos los panoramas deben ser alcanzables desde startPanoramaId. No deben quedar puntos aislados.

-------------------------------------------------------------------------------
7. CÓMO CONECTAR PANORAMAS CORRECTAMENTE
-------------------------------------------------------------------------------

El recorrido es un grafo:

- Cada panorama es un nodo.
- Cada flecha es un enlace.
- targetId identifica el nodo de destino.

Regla obligatoria del proyecto:

Si A conecta con B, B debe conectar con A.

Ejemplo correcto:

A.links contiene targetId: 'b'
B.links contiene targetId: 'a'

El yaw de regreso no tiene que ser matemáticamente opuesto porque cada panorama puede tener una orientación distinta. Debe ajustarse mirando la imagen de destino.

No se permite:
- Un panorama conectado consigo mismo.
- Un targetId inexistente.
- Una conexión sin regreso.
- Un panorama aislado del inicio.
- Dos panoramas con el mismo id.

Antes de programar, conviene dibujar el mapa de conexiones:

Portería ↔ Acceso principal ↔ Recepción ↔ Pasillo central
                                           ├── Cuarto de control
                                           ├── Escalera norte ↔ Piso 2
                                           └── Almacén ↔ Punto 2 ↔ Punto 3

Este mapa permite detectar rutas sin salida, conexiones olvidadas y nombres ambiguos.

-------------------------------------------------------------------------------
8. CÓMO AJUSTAR YAW Y PITCH
-------------------------------------------------------------------------------

yaw controla la dirección horizontal:

0       frente
90      derecha
-90     izquierda
180     detrás
-180    detrás

El rango válido es -180 a 180 grados.

pitch controla la inclinación vertical:

0       horizonte
positivo hacia arriba
negativo hacia abajo

El rango válido es -90 a 90 grados.

Para una flecha sobre el piso suele funcionar inicialmente un pitch entre -8 y -18. Para subir una escalera puede usarse un valor positivo. Estos son puntos de partida, no valores universales.

Procedimiento de ajuste:

1. Crear la conexión con yaw aproximado.
2. Ejecutar npm run dev.
3. Abrir el panorama.
4. Observar dónde aparece la flecha.
5. Aumentar o disminuir yaw hasta alinearla con la puerta o ruta.
6. Ajustar pitch para ubicarla a una altura cómoda.
7. Verificar la flecha de regreso de forma independiente.
8. Probar en computador y celular.

No se debe asumir que la flecha de regreso es yaw + 180. La orientación cero depende de cada archivo panorámico.

-------------------------------------------------------------------------------
9. CÓMO AGREGAR UN PISO
-------------------------------------------------------------------------------

Agregar un objeto dentro de floors:

{
  id: 'piso-03',
  name: 'Tercer piso',
  rooms: [
    // Ambientes del tercer piso.
  ],
}

El piso debe contener al menos un ambiente. Para conectarlo con el resto del recorrido debe existir una transición física bidireccional:

- Escalera inferior ↔ escalera superior.
- Ascensor piso 2 ↔ ascensor piso 3.
- Rampa inferior ↔ rampa superior.

El nuevo piso aparecerá automáticamente como grupo en el menú.

-------------------------------------------------------------------------------
10. ESPACIOS EXTERIORES, ESCALERAS Y ASCENSORES
-------------------------------------------------------------------------------

Los exteriores pueden modelarse como un piso llamado Exterior o Nivel exterior.

Las escaleras pueden tratarse como ambientes con varios puntos:

Escalera norte
  - Base
  - Descanso 1
  - Descanso 2
  - Llegada

En instalaciones grandes es mejor evitar saltos visuales demasiado largos. Si el usuario no puede comprender cómo llegó al destino, debe agregarse un punto intermedio.

Para un ascensor pueden usarse nodos por nivel. La interfaz debe dejar claro el piso de destino. Si se desea simular una selección de pisos distinta a una flecha espacial, se requerirá una mejora específica de interfaz.

-------------------------------------------------------------------------------
11. QUÉ VALIDACIONES YA REALIZA EL PROYECTO
-------------------------------------------------------------------------------

src/domain/validate-tour.ts comprueba:

- Que exista al menos un piso.
- Que cada piso tenga ambientes.
- Que cada ambiente tenga panoramas.
- Que los id de pisos no se repitan.
- Que los id de ambientes no se repitan en todo el recorrido.
- Que los id de panoramas no se repitan.
- Que entryPanoramaId pertenezca al ambiente.
- Que startPanoramaId exista.
- Que las rutas de imágenes sean locales y seguras.
- Que targetId exista.
- Que un panorama no se enlace consigo mismo.
- Que yaw y pitch estén dentro de rango.
- Que cada conexión tenga regreso.
- Que todos los panoramas sean alcanzables desde el inicio.

src/domain/validate-tour.test.ts también comprueba que cada archivo configurado exista dentro de public.

Estas validaciones detectan errores estructurales. No pueden saber si una flecha apunta visualmente hacia la puerta correcta; eso requiere revisión en navegador.

-------------------------------------------------------------------------------
12. PROCESO COMPLETO PARA AGREGAR ESPACIOS
-------------------------------------------------------------------------------

1. Definir el objetivo del nuevo sector.
2. Dibujar su mapa de ambientes y conexiones.
3. Asignar códigos únicos siguiendo la convención.
4. Preparar el inventario de panoramas artificiales.
5. Verificar que cada imagen sea equirectangular 2:1.
6. Copiar las imágenes a public/panoramas/demo.
7. Agregar pisos, ambientes y panoramas en el archivo de datos.
8. Definir entryPanoramaId para cada ambiente.
9. Crear todas las conexiones de ida y regreso.
10. Ejecutar npm run check.
11. Ejecutar npm run dev.
12. Ajustar yaw y pitch visualmente.
13. Recorrer todas las rutas hacia adelante y hacia atrás.
14. Probar menú, teclado, celular, recarga y cierre de sesión.
15. Actualizar los TXT y las pruebas automatizadas.
16. Publicar una vista Preview.
17. Validar Preview desde otra red.
18. Publicar Production únicamente después de aprobación.

-------------------------------------------------------------------------------
13. LISTA DE INVENTARIO RECOMENDADA
-------------------------------------------------------------------------------

Antes de programar, mantener una tabla con estas columnas:

- Código de instalación.
- Piso.
- Código de ambiente.
- Nombre visible.
- Código de panorama.
- Nombre del punto.
- Nombre del archivo.
- Panorama de entrada: sí o no.
- Destinos conectados.
- Estado de la imagen.
- Estado de yaw y pitch.
- Prueba de ida.
- Prueba de regreso.
- Observaciones.

Ejemplo:

Instalación: demo-01
Piso: p01
Ambiente: p01-recepcion
Panorama: p01-recepcion-001
Archivo: p01-recepcion-001.png
Entrada: sí
Conecta con: p01-acceso-001, p01-pasillo-001
Estado: probado

Para decenas de panoramas puede usarse una hoja de cálculo como fuente de control. No debe convertirse automáticamente en código sin validación.

-------------------------------------------------------------------------------
14. CUÁNDO EL ARCHIVO DEMO-TOUR.TS DEJA DE SER SUFICIENTE
-------------------------------------------------------------------------------

El archivo actual es apropiado para una demo pequeña. Debe dividirse cuando:

- Existan varias instalaciones.
- El archivo sea difícil de revisar.
- Diferentes personas editen sectores distintos.
- Haya decenas o cientos de panoramas.
- Se requieran permisos por instalación.
- Los recorridos cambien con frecuencia.

Primera separación recomendada:

src/data/tours/
  demo-01/
    tour.ts
    piso-01.ts
    piso-02.ts
  demo-02/
    tour.ts
    exterior.ts

Segunda etapa, para escala empresarial:

- Base de datos de instalaciones, pisos, ambientes y panoramas.
- Panel administrativo con formularios validados.
- Almacenamiento de imágenes separado del código.
- Versiones de recorridos.
- Flujo borrador, revisión, aprobación y publicación.
- Importador controlado desde CSV o JSON.
- Auditoría de cambios.

No se recomienda mantener cientos de panoramas escritos manualmente en un único archivo TypeScript.

-------------------------------------------------------------------------------
15. MODELO PROPUESTO PARA MÚLTIPLES INSTALACIONES
-------------------------------------------------------------------------------

Una evolución del dominio podría ser:

Organización
  └── Instalaciones
       └── Recorridos o versiones
            └── Pisos
                 └── Ambientes
                      └── Panoramas
                           └── Enlaces

Campos futuros de una instalación:

- id interno opaco.
- code empresarial.
- name visible.
- region.
- status: borrador, revisión, publicado o archivado.
- currentTourVersionId.
- createdAt y updatedAt.

Campos futuros de un recorrido:

- version.
- startPanoramaId.
- publishedAt.
- publishedBy.
- changeSummary.

Esto permite actualizar una instalación sin reemplazar inmediatamente la versión aprobada.

-------------------------------------------------------------------------------
16. RENDIMIENTO A GRAN ESCALA
-------------------------------------------------------------------------------

Cada panorama comprimido ocupa más memoria al decodificarse. Cien archivos pequeños pueden bloquear un teléfono si se precargan simultáneamente.

Antes de ampliar significativamente se debe:

- Desactivar la precarga global de todos los nodos.
- Precargar solamente panoramas vecinos cuando sea necesario.
- Medir tiempo de carga y memoria en celulares de gama media.
- Usar dimensiones y compresión apropiadas.
- Considerar WebP o JPEG para imágenes fotográficas.
- Incorporar miniaturas cuando exista un catálogo de instalaciones.
- Dividir recorridos por instalación y cargar solo el seleccionado.
- Evaluar mosaicos equirectangulares para imágenes muy grandes.
- Configurar caché sin conservar indefinidamente versiones obsoletas.

La fase 7 ya separó el visor del paquete inicial mediante importación dinámica. Sin embargo, panorama-viewer.ts conserva preload: true para la demo de ocho imágenes. Esa opción debe revisarse antes de llegar a decenas de panoramas.

-------------------------------------------------------------------------------
17. PRUEBAS NECESARIAS A GRAN ESCALA
-------------------------------------------------------------------------------

Pruebas estructurales:
- Identificadores únicos.
- Archivos existentes.
- Entrada válida por ambiente.
- Enlaces bidireccionales.
- Ningún panorama aislado.
- Ángulos dentro de rango.

Pruebas funcionales:
- Abrir cada ambiente desde el menú.
- Recorrer cada enlace de ida y regreso.
- Volver al inicio desde cualquier piso.
- Cambiar de piso mediante escaleras o ascensores.
- Comprobar el contador de ubicaciones.
- Cerrar y abrir el menú móvil.

Pruebas de error:
- Archivo inexistente.
- Imagen dañada.
- Red lenta.
- Red interrumpida.
- WebGL no disponible.
- Sesión terminada durante una carga.

Pruebas de rendimiento:
- Primera carga.
- Cambio entre panoramas.
- Memoria después de recorrer muchos puntos.
- Comportamiento en computador y celular.
- Consumo de datos.

Pruebas de aceptación:
- Una persona sin conocimiento técnico puede comprender la navegación.
- Las flechas representan rutas físicamente coherentes.
- Los nombres visibles son claros.
- No existen rutas sin salida accidental.
- El responsable aprueba el mapa completo.

-------------------------------------------------------------------------------
18. CONTROL DE CAMBIOS Y VERSIONES
-------------------------------------------------------------------------------

Cada ampliación debe registrar:

- Fecha.
- Instalación afectada.
- Pisos y ambientes añadidos.
- Panoramas añadidos o reemplazados.
- Conexiones modificadas.
- Responsable del cambio.
- Resultado de npm run check.
- Resultado de la revisión manual.
- URL Preview aprobada.
- Autorización de publicación.

No se debe modificar Production directamente para probar conexiones. El flujo correcto es local, pruebas, Preview, aprobación y Production.

-------------------------------------------------------------------------------
19. ERRORES COMUNES Y CÓMO EVITARLOS
-------------------------------------------------------------------------------

Error: reutilizar cuarto-01 en dos pisos.
Solución: incluir el piso o sede en el id.

Error: agregar A -> B y olvidar B -> A.
Solución: registrar conexiones por pares y ejecutar npm run check.

Error: entryPanoramaId apunta a otro ambiente.
Solución: usar un id contenido en panoramas del mismo ambiente.

Error: la imagen existe pero la ruta contiene public/.
Solución: usar panoramas/demo/archivo.png.

Error: crear un botón manual en HTML.
Solución: agregar el ambiente a TourConfig; el menú se genera automáticamente.

Error: usar una sola imagen para representar un espacio demasiado largo.
Solución: añadir puntos intermedios dentro del mismo ambiente.

Error: asumir yaw de regreso igual a yaw de ida más 180.
Solución: ajustar cada panorama visualmente.

Error: publicar cientos de imágenes desde un único recorrido.
Solución: dividir por instalación, cargar bajo demanda y medir memoria.

Error: cambiar nombres de id después de publicar sin revisar enlaces.
Solución: considerar los id como claves estables y migrarlos de forma controlada.

-------------------------------------------------------------------------------
21. CRITERIO PARA CONSIDERAR COMPLETA UNA AMPLIACIÓN
-------------------------------------------------------------------------------

Una ampliación está completa solamente cuando:

- Todas las imágenes artificiales existen y son 2:1.
- Todos los id cumplen la convención y son únicos.
- Cada ambiente tiene una entrada válida.
- Todas las conexiones tienen regreso.
- No existen panoramas aislados.
- Las flechas están alineadas visualmente.
- El menú y el contador se actualizan.
- npm run check termina correctamente.
- El recorrido fue probado en computador y celular.
- La documentación fue actualizada.
- Una Preview fue revisada desde otra red.
- Existe autorización para publicar en Production.

-------------------------------------------------------------------------------
22. RESUMEN OPERATIVO
-------------------------------------------------------------------------------

Para agregar un espacio:

1. Nombrar piso, ambiente, panorama y archivo.
2. Copiar la imagen artificial 2:1.
3. Agregar el ambiente o panorama al archivo de datos.
4. Definir entryPanoramaId.
5. Conectar ida y regreso.
6. Ejecutar npm run check.
7. Ajustar flechas en el navegador.
8. Probar todas las rutas.
9. Documentar y aprobar antes de publicar.

Para escalar:

1. Definir códigos de instalaciones.
2. Separar recorridos por instalación.
3. Mantener inventario central.
4. Evitar precarga global.
5. Medir rendimiento.
6. Migrar a datos administrables y versionados cuando la edición manual deje de ser segura.

Este documento describe el modelo actual y la ruta de crecimiento. No autoriza por sí mismo el uso de imágenes reales ni reemplaza la revisión de seguridad prevista para una versión empresarial.
